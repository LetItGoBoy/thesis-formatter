# 《雾港谜案》故事圣经（MVP）

## 项目定位

《雾港谜案》是「数据库原理」课程的 SQL 侦探推理游戏 IP。

它不把 SQL 当语法来背，而是让学生扮演查档侦探：每条线索都要写一句真实 SQL 去数据库里查，逐层缩小嫌疑范围，最后指认真凶。破案的过程，就是关系查询的过程。

核心理念：

> 侦探破案的循环——搜证 → 查询 → 求交 → 锁定真凶——本身就是关系数据库查询。

技术形态：浏览器内置 SQLite（sql.js / WASM），纯前端运行，无后端、无登录、无存档。学生写的每一句 SQL 都真实执行、即时反馈。

## 世界观

雾港，一座常年浸在海雾里的港口城市。城市的市民档案、健身房打卡、车辆登记都沉淀在「城市档案数据库」里。普通人只看到结果，侦探却能用 SQL 直接质询这些记录。

## 案件（MVP 单案）

2024-01-15 深夜，雾港大剧院后巷发现一具尸体。现场报告留下两条**互相独立**的线索：

1. 凶手当晚在「雾港健身房」打过卡；
2. 逃离时车牌被记下，含字符 `X7`。

八名市民中，单看任一条线索都会命中好几个人；只有**两条线索同时成立**的那一个才是真凶——这正是 `JOIN` 求交集的意义。

真凶：**高金**（当晚打卡者 {2,5,7} ∩ 车牌含 X7 者 {3,5,8} = {5}）。

## 数据库表（4 张小表）

| 表 | 作用 |
|---|---|
| `crime_scene_report` | 现场报告（线索入口） |
| `people` | 市民档案（id ↔ 姓名） |
| `gym_checkin` | 健身房打卡记录 |
| `cars` | 车辆登记（车牌） |

## 关卡 ↔ 知识点（层层递进）

| 关 | 知识点 | 玩家要做的 |
|---|---|---|
| 线索 01 | `SELECT` / `WHERE` | 用三重条件查出案发现场报告 |
| 线索 02 | `WHERE` 集合筛选 | 查当晚打卡的所有 person_id（命中 3 人） |
| 线索 03 | `JOIN` 多表求交 | 连接三表，求「当晚打卡 ∧ 车牌含 X7」的唯一交集 |
| 结案 | 综合推理 | 指认真凶姓名 |

## 校验原则

宽松判定：玩家查询结果**包含关键行**即通关，不强求写法与参考答案一致。卡住时提供文字提示，再卡可展开参考答案——降低劝退，保住成就感。

## 后续可扩展（本 MVP 不做）

- 多案件、案件难度梯度（子查询、GROUP BY、聚合、事务/隔离级别做「洗钱案」）
- 进度存档与登录、错题回看
- AI 侦探搭档给自然语言提示
- 排行榜 / 最少查询数通关挑战
